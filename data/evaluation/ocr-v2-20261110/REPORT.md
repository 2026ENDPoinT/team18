전체 입력은 실제 문서 3개와 합성 문서 6개의 원본·축소본·흐림본 18장으로 총 21장이다. 원본은 총 9개이고 변형본은 12장이다. 실제 3번째 PDF는 두 인쇄면을 담은 1개 PDF 페이지다. 수치의 분모는 모든 평가 입력의 문자 수이며 변형본은 독립된 원본이 아니다.

본문만 있는 합성 프로젝트·공고는 대체로 잘 읽지만, 표에서는 셀의 출력 순서와 성적 0/O 혼동이 관측됐다. 실제 교육운영계획은 양쪽 인쇄면의 표를 같은 세로 위치 기준으로 섞어 읽어 CER이 매우 높았다. 공백 제거 CER도 순서 오류를 포함하므로 이를 순수한 글리프 분류 오류율로 해석할 수 없다. 이 시험은 소규모 목적 표본이며 휴대폰 촬영·손글씨·복합 스캔 전반의 정확도를 입증하지 않는다.

## 실행 경로와 평가 경계

- `ai/local/ocr.py:43`의 `LocalOCR`가 엔진이다. 인식 클래스는 `PPOCRV6SmallRecForTextRecognition`(6,671,094 parameters), 검출 클래스는 `PPOCRV6SmallDetForObjectDetection`(2,460,709 parameters)다. 인식기는 Qota-OCR 기반 NCS 합성 한 줄 추가 학습 모델이며 CTC 출력층을 튜닝했다. 다른 OCR 엔진이나 원본 Qota-OCR로 대체하지 않았다.
- `ai/workflow.py:66`의 create → `ai/intake.py:54`에서 이미지 형식/크기 확인 → `ai/intake.py:68`의 `LocalOCR(local)` → `extract(png, bytes)` → `read_image` 순서다. 이 평가도 정확히 같은 `LocalOCR(local).extract`를 호출했다.
- `read_image`는 RGB 변환, 4방향(0/90/180/270도) 검출과 후보 줄 신뢰도로 방향 선택, 기본 rows 정렬, 최대 500개 영역 crop, 필요한 세로 crop의 90도 회전, 인식 전처리·CTC 인식, 줄별 strip 및 LF 연결을 한다. padding은 0이다. 검출 threshold 0.2 / box_threshold 0.45 / unclip_ratio 1.4를 유지했다.
- 검출 전처리 설정은 limit_side_len=736, limit_type=min, max_side_limit=4000과 BGR/정규화다. 인식 전처리는 높이 48, 기본 폭 320, 최대 폭 3200 및 패딩/정규화다. 저장된 processor 설정을 그대로 로딩했다.
- OCR 텍스트는 `ai/intake.py:71`에서 누적되어 `:89`의 `extracted_text`에 저장된다. `ai/workflow.py:29`에서 analyze가 Node 생성기를 호출하고, `ai/gemini/roadmap.mjs:89`의 Gemini 요청은 해당 JSON을 text로 보낸다. Gemini가 원본 이미지를 읽는 구조가 아니며 독립 OCR 출력이 있다. 이번 실행에서는 Gemini 경로를 전혀 호출하지 않았다.

## 평가 데이터와 중복 점검

저장소의 `docs/test-files`에는 가상 프로젝트 TXT/PDF/DOCX 등이 있지만 전체 실제 이미지에 대한 독립 CER 정답은 없었다. `ai/local/ocr-*.json`은 한 줄 합성 시험 또는 일부 문구 포함 여부 결과이고, 실제 이미지 원본 및 NCS 학습 CSV는 체크아웃에 없었다. 기존 0.3% CER과 14/24 문구 포함 결과는 이번 전체 페이지 CER과 직접 비교할 수 없다.

실제 PDF는 ONTHEIT/KDoc-OCRBench-V2의 고정 revision `e94ba5be6b3c6ec4fed85b0789fc73395f6930fb`에서 골랐다. 자료의 기존 OCR/LLM 부분 문구 정답을 CER 정답으로 쓰지 않았다. 새 정답은 PDF 렌더링과 원 디지털 텍스트를 대조하면서 수동으로 순서를 정리했고, 이미지 해시·정답 해시·채점 규칙을 추론 전에 고정했다. 검수자는 이 평가를 수행한 에이전트 1개이며 사람 이중 검수가 아니므로 잔여 전사 오류 가능성이 있다.

기존 평가 스크립트의 Notices/Manuals/Reports 정렬 인덱스 0~3(개발 및 이전 benchmark 브랜치 포함)과 이번 실제 파일 3개는 겹치지 않는다. 기존 추적 이미지/PDF와도 파일 해시 중복이 없고, 기존 평가 기록 및 이전 benchmark 스크립트에 전체 정답 문서가 일치하지 않는다. 다만 NCS 원문·학습/검증 이미지 명세와 원 모델의 전체 사전학습 자료가 없어 문구/원본 단위의 완전한 비중복은 증명할 수 없다. 일반 과목명·기술 용어가 중복될 가능성도 있다. `data_audit.json` 참조.

합성 6개는 원문 JSON을 먼저 작성하고 Nanum Gothic 또는 Nanum Myeongjo로 1240×1754 PNG에 렌더링했다. 한글 글리프 존재, 모든 글자 bbox와 표 셀 범위를 검사하고 시각 검수했다. 축소는 Lanczos 50%(620×877), 흐림은 원본 크기에서 Gaussian radius=1.2다. 원본 6개에 변형 12개를 추가했으며 원문은 같다.

표는 행 우선, 각 행의 왼쪽→오른쪽, 셀 내부는 위→아래로 읽는다. 병합 셀은 첫 행에 한 번만 쓰고 탭으로 셀, LF로 행/시각적 줄을 구분했다. real_03 펼침면은 왼쪽 면 전체 후 오른쪽 면 전체다. 머리말·꼬리말·페이지 번호·글자 형태 글머리표는 포함하고 장식 도형은 제외했다. 이는 예측 확인 전에 고정한 `protocol.md`의 규칙이다.

## CER과 상태 집계

정답과 예측 양쪽에 NFC만 적용했다. 공백 포함판은 LF/탭/공백을 그대로 유지한다. 공백 제거판은 모든 `str.isspace()` 문자를 제거한다. 영문 대소문자·숫자·문장부호는 그대로 둔다. 각 문서의 Levenshtein 삽입(I), 삭제(D), 치환(S) 횟수를 합친 뒤 전체 정답 문자 수로 나누었다. 문서별 CER의 산술평균이 아니다.

전체 공백 포함 CER = (I 550 + D 658 + S 563) / 8,864 = 1,771 / 8,864 = 19.979693%. 모든 공백 제거 CER = (I 443 + D 500 + S 186) / 6,700 = 1,129 / 6,700 = 16.850746%.

입력 21 / 비어 있지 않은 반환 21 / 빈 출력 0 / 장당 추론 오류 0. 빈 출력은 모든 정답 문자를 삭제로 채점하도록 구현했다. 실행 오류도 별도 상태로 남기고 보수적으로 빈 문자열로 채점해 전체에 포함하며, 오류 없는 반환만의 집계도 저장한다. 이번에는 두 집계가 같다. 준비 중의 pip DNS 제한과 메타데이터 sysctl 오류는 모두 복구했고 샘플 추론 오류와 구분했다.

## 장치와 시간

Apple M4, CPU 10코어(성능 4·효율 6), RAM 16GB, macOS 26.7.2 arm64. 실행 장치는 `cpu`이며 GPU/CUDA/MPS를 사용하지 않았다. 서비스 코드가 CUDA 유무만으로 장치를 선택한다. PyTorch thread=2, interop=1, Python 3.12.12, torch 2.15.0, torchvision 0.29.2, transformers 5.22.2, Pillow 13.0.0, OpenCV 5.0.0.93, PDFium 5.15.2다.

torch 및 OCR 모듈 import: 0.552초. 첫 `LocalOCR` 생성(Transformers 관련 로딩 포함): 19.283초. 별도 준비 이미지 1장: 1.481초. 세 시간 모두 장당 시간 집계에서 제외했다. 입력 21장 각각 한 번씩 측정했으며 중앙값 2.365초, 범위 1.329~6.478초다.

측정 시작은 PNG bytes가 메모리에 준비된 시점의 `engine.extract` 호출 직전, 종료는 텍스트 반환 직후다. PNG 디코딩, RGB 변환, 방향 판별·검출·인식·정렬을 포함한다. 모델 초기화, 파일 디스크 읽기, PDF 렌더링, 정답 채점, HTTP/업로드와 Gemini 호출은 포함하지 않는다. 반복 측정 분산·동시 처리량·GPU 성능은 이번 시험 범위에 없다.

## 재현 및 검증

`README.md`의 명령으로 고정 입력·정답을 같은 커밋에서 재실행할 수 있다. `requirements.lock.txt`는 실제 설치된 전체 버전이다. 실행에는 API 키나 추가 가중치 다운로드가 필요 없다. `results/environment.json`에 실제 클래스, 설정, 모델/코드 해시와 시간 정의를 기록했다.

`evaluate.py`는 서비스 OCR을 그대로 import하고 모델/서비스 파일의 해시가 실행 전후 같음을 확인한다. `verify_metrics.py`는 별도 표준 라이브러리 동적계획법으로 21장×2지표=42개 편집거리 및 전체 가중 집계를 재계산했다. 전부 일치했다(`results/verification.json`).

샘플별 정답: `ground_truth/<original_id>.txt`; 원 입력: `images/<sample_id>.png`; 무보정 예측: `results/predictions/<sample_id>.txt`; 점수: `results/sample_scores/<sample_id>.json`. 전체 CSV는 `results/scores.csv`, 전체 JSON은 `results/summary.json`이다. `manifest.json`에서 모든 ID와 경로를 대응시킬 수 있다.

실제 원본 출처: [ONTHEIT/KDoc-OCRBench-V2](https://huggingface.co/datasets/ONTHEIT/KDoc-OCRBench-V2). 원문 제공기관 URL과 각 PDF의 이용조건은 `sources/real_sources.json`에 고정했다. [Qota-OCR 모델 카드](https://huggingface.co/atonlee/Qota-OCR)는 기본 인식기의 배경 정보이며 카드에 있는 점수를 이번 결과로 사용하지 않았다.
